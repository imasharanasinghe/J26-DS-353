Pedagogy-typed knowledge graphs for verified personalized learning paths

From four checked pipelines to one system that watches, adapts and proves it

After Progress Presentation 1, the panel said each component is not sufficient on its own and asked for add-ons, including learner behaviour analysis with computer vision and a better user experience. This guide gives each member a concrete plan: what to add, how to build it, how to evaluate it, and what to show at PP2 in February 2027.

What the panel said

The components are insufficient. Add add-ons to each component. Analyse user behaviour, for example with computer vision. Think about the technical side and a better user experience.

What this means in practice

Today every component only sees correct or wrong answers and text. None of them notices how the student behaves. Each member also needs a larger, clearly owned research contribution that a topological sort or a rule script cannot match.

The core idea

Close the loop: sense, model, plan, explain, sense again

Add one behaviour sensing layer that every component uses. Each member then owns one major research add-on, one or two supporting add-ons and one user-facing feature. The safety story of the project stays the same: nothing reaches the student without passing a rule check.

Rules for the whole plan

Three principles that keep the project defensible

Keep the safety invariant

Every new adaptive feature (replanning, bandits, strategy switching) only chooses among options that already passed the rule check. This is the project's strongest story; do not weaken it.

Behaviour is optional input

Everything must still work with the camera off. Camera signals improve decisions; they never block them. This also makes the ethics case much easier.

Each add-on has its own RQ

An add-on without a research question and a baseline is just a feature. Every add-on below lists the question, the metric and what it is compared against.

COMPONENT 1 / RANASINGHE R A I K

Multimodal, self-correcting knowledge graph

Uniqueness: every edge carries evidence from three sources (lecture text, lecture visuals and real learner behaviour), and the graph flags its own wrong edges when learner data disagrees.

Now: 84 concepts 101 verified edges Gold accuracy 63% Gold set 30 chunks Kappa 0 (label mismatch)

Where it stands

  • Rule-based extraction from transcripts and the MOOC concept set, with a symbolic checker before saving.
  • Four typed edges in Neo4j AuraDB, used by C2, C3 and C4.
  • LLM extractor and fine-tuning are listed as next steps.

What the panel will see as thin

  • It reads as a data pipeline with phrase rules. The AI part is not built yet.
  • The graph is static once built, and nothing checks whether edges match how students actually learn.
  • Nodes hold no learning material, so C3 and C4 cannot point a student to the right part of a lecture.

Fix first (before any add-on)

  • Write a one-page annotation guideline with fixed label names and five worked examples per edge type. Re-label, then report Cohen's Kappa again.
  • Grow the gold set to at least 100 chunks, with at least 15 misconception cases.
  • Finish the LLM extractor and report it against the rule baseline per edge type. This becomes the text-only baseline for Add-on 1.

ADD-ON 1.1

Lecture video vision pipeline

MustCVResearch

Read the lecture videos, not only the transcripts. Detect each slide, read its text and code, recognise the diagram type, and line it all up with what the lecturer says at that moment. Slides become a second source of edge evidence, and every concept node links to the exact video segment that teaches it.

  1. Get the videos behind the 59 transcripts. If they are not available, use SLIIT DSA lecture recordings with the lecturer's permission. If transcripts have no timestamps, regenerate them with Whisper to get word-level times.
  2. Detect slide changes with PySceneDetect (content detector) and keep one key frame per slide.
  3. Split each key frame into title, bullet text, code and diagram regions with a layout detector (LayoutParser or a YOLO layout model). Fine-tune on about 200 hand-labelled frames if the default model misses code blocks.
  4. Run OCR (PaddleOCR) on text and code regions. Train a small CNN to classify diagrams into array, linked list, tree, heap, graph, table or other, using about 300 labelled crops.
  5. Align slide text with the transcript window of the same time span. Run the same concept spotting and relation extraction on slide text and merge with transcript evidence.
  6. Store on each node a list of segments {video_id, start_s, end_s, frame_id}, and on each edge an evidence list with a source field: text, slide or learner.
Tools

PySceneDetect, LayoutParser or a YOLO layout model, PaddleOCR, PyTorch, Whisper

Feeds

C3 uses segments as the resource for each path step. C4 shows the exact clip or frame inside an explanation.

Measure

Edge F1 for text only versus text plus slides; slide-change detection accuracy; OCR character error rate; diagram classifier accuracy.

ADD-ON 1.2

Self-correcting edges from learner evidence

ShouldResearch

Test each prerequisite edge against how students actually perform. If A is really a prerequisite of B, learners who have not mastered A should do clearly worse on B. Edges with no support get flagged, and strong dependencies with no edge become candidate edges. Nothing is changed automatically: suggestions go to the curation console, so the graph stays verified.

  1. Use exercise logs mapped to concepts: MOOCCubeX (already planned for C3) and later the pilot data from the team app.
  2. For each edge A to B, compare success on B between learners with high and low mastery of A (mastery from C2). Compute a support score and a confidence interval with a bootstrap.
  3. Flag edges whose interval includes zero. Propose new edges where the gap is large and no edge exists. Write the score into the edge evidence with source: learner.
Measure

Ask a lecturer to judge flagged and proposed edges blind. Report the precision of flags and proposals.

Why it matters

It turns C1 from a one-time build into a graph that improves with use. That is a clear research contribution that a rule pipeline does not have.

Link to C4

C4's Graph Auditor supplies the audit method (implication, order and lift tests, plus a Bloom audit) and tests it on planted errors. Its edge statuses arrive here as proposals for the curation console, and C1 applies what a lecturer approves.

ADD-ON 1.3

Instructor curation console with active learning

ShouldUXResearch

A screen where a lecturer reviews edges. The queue is ordered by uncertainty: low extractor confidence, disagreement between text and slide evidence, or conflict with learner evidence. Each item shows the source sentence, the slide frame and the learner statistics. Approve, reject or retype. Decisions go back into the extractor as new training labels.

Research angle

Compare uncertainty-ordered review with random order. How many labels are needed to reach the target F1?

UX extras

Graph view filtered by edge type, search by concept, and a click-through from any node to its video segments.

CouldResearch

ADD-ON 1.5

Graph export with facts and versioned edges

ShouldIntegrationSuggested by C4

C4 and C2 need to read the graph without going through Neo4j, and the audit and lecturer approvals need somewhere to be stored. This is also the first step towards a layered, versioned graph.

  • JSON export with stable concept ids and the four edge types, next to the CSV and Neo4j outputs. Make the Neo4j write safe: the last stage should write a new version, not wipe the database first.

  • Edge fields source (seed, caption, slide, learner, lecturer), status, confidence and a graph_version, so audit results and lecturer approvals have a place to live.

ADD-ON 1.6

Layered graph and weekly update mode

CouldResearchSuggested by C4

"Dynamic" should mean layers, versions and proposals, not a graph that rewrites itself.

  • Layers: a base graph at department level, a lecturer overlay per lecturer and offering (reorder, add local concepts, mark "not covered", change emphasis, add terms), and audited confidence per offering.
  • Weekly update: re-run extraction on one new lecture and produce a diff, not a full rebuild. Every change is a proposal that a lecturer approves, with a version and a changelog. The graph is frozen for each 7-week block.
  • Stable ids: if a concept is split, merged or renamed, learner mastery moves with it (a split keeps the parent's mastery with more uncertainty; a merge takes the lower mastery).

Questions the panel will likely ask

Isn't this just OCR on slides?

No. OCR is one step. The contribution is multimodal evidence per edge, with a measured gain in F1 over text only, plus linking each concept to the exact teaching segment.

What if learner evidence contradicts an expert edge?

The edge is flagged, not removed. A lecturer decides in the console. The graph stays verified, and the decision becomes training data.

COMPONENT 2 / SAWANDI D E P

Behaviour-aware learner model

Uniqueness: one model that reports what the learner knows, how sure it is, and how the learner is doing right now (engaged, confused, bored or frustrated), using a webcam model that runs entirely in the browser.

Matches DKT on AUC Ahead with 1 to 3 past answers Graph gain +0.004 AUC Error detection 0.56 vs 0.65

What to build

ADD-ON 2.1

In-browser engagement and affect detection

MustCVResearch

This is the main computer vision add-on the panel asked for. A webcam model running in the student's browser estimates four states (engaged, confused, bored, frustrated) every few seconds. Video never leaves the device. Only the state label and a confidence value are sent to the server.

  1. Run MediaPipe Face Landmarker in the browser. Per frame it gives face landmarks (including iris points), 52 blendshape scores and a head pose matrix.
  2. Build features over 2-second windows at about 10 frames per second: head yaw and pitch variance, gaze away-from-screen ratio, eye aspect ratio and blink rate, brow lowering and inner brow raise (confusion cues), jaw open (yawning), and the share of frames with no face.
  3. Train on DAiSEE (9,068 clips from 112 people, each labelled for boredom, confusion, engagement and frustration at four levels). Extract the same features offline with MediaPipe in Python so training and browser features match exactly.
  4. DAiSEE labels are imbalanced. Collapse each state to low versus high, and use class weights. Start with gradient boosting, then try a small GRU over windows.
  5. Export the model to ONNX and run it with onnxruntime-web, or train it directly in TensorFlow.js. Check it runs above 10 frames per second on a normal student laptop.
  6. Build the consent screen, a visible camera indicator and a pause button. If the camera is off, the system falls back to interaction signals only.
Tools

MediaPipe Tasks Vision (JS and Python), scikit-learn or LightGBM, PyTorch, onnxruntime-web

Feeds

C3 uses the state as a replanning trigger. C4 uses confusion to switch explanation strategy. C2 uses it as a feature.

Measure

Per-state F1 on the DAiSEE test split; frames per second in the browser; agreement with pilot students' own ratings ("How confused are you right now?", 1 to 5).

ADD-ON 2.2

Behaviour-informed knowledge tracing

MustResearch

Feed how the learner answered into the GNN, not only whether the answer was right. This lets the model separate a lucky guess from real knowledge and a careless slip from a real gap.

  1. Per attempt, add: response time normalised per item, hint count, answer changes, idle time, tab switches (Page Visibility API), video pauses and rewinds before the attempt, and the affect state during the attempt when available.
  2. Concatenate these features with the interaction embedding in the GNN. Pre-train on public datasets that include timing and hints (ASSISTments 2012, Junyi Academy, EdNet), then fine-tune on programming data.
  3. Add guess and slip flags: a very fast correct answer while disengaged lowers confidence; a slow wrong answer with confusion signals a real gap.
Measure

AUC and ECE with and without behaviour features, reported separately for 1 to 3 past answers (cold start).

Ablation

Answers only, plus timing and hints, plus affect. This shows which signal helps.

ADD-ON 2.3

Uncertainty that tracks missing evidence

MustResearch

Your own results show MC Dropout uncertainty rises with more answers and detects errors worse than the plain probability (0.56 versus 0.65). Fix this directly, because C3's "probe uncertain topics" rule depends on it.

  • Compare a deep ensemble (5 models) and an evidential output head with MC Dropout.
  • Add split conformal prediction on top, so each mastery value comes with an interval that has a guaranteed coverage rate.
  • Add an evidence term: concepts with no direct attempts and weak graph support must get wider intervals.
  • Also test a simple evidence-count uncertainty (for example a Beta distribution per concept) against MC Dropout. Either result is useful and honest.
Target

Error detection AUROC above the plain probability (0.65), and uncertainty that falls as evidence grows.

ADD-ON 2.4

Learner knowledge map

ShouldUX

A visual map of the concept graph for the student. Colour shows mastery; hatching shows uncertainty. A "Check me" button on an uncertain concept asks C4 for a short probe. Each question also gets an "I'm not sure" button, which becomes one more signal for the model. C4 teach-back exams add evidence per concept and Bloom level, so the map can show mastery by level.

ADD-ON 2.5

Mastery per Bloom level and teach-back evidence

ShouldIntegrationSuggested by C4

The panel's comment is about cognitive level over time, so the learner state should say what the learner can do at each Bloom level, not only whether a concept is known.

  • State: for each learner, concept and Bloom level, a mastery probability and an uncertainty. Not one number per concept, because the Bloom question has to be testable. A concept is mastered at level L when probability is at least 0.70 and uncertainty is at most 0.25.
  • Accept the evidence message from C4's teach-back exam (learner, concept, level, score, items, weight, graph version) through an evidence endpoint. It is a second kind of data besides right and wrong answers.
  • Evidence weights: teach-back exam high once validated, checkpoint quiz high, practice attempts medium (lower if hints were used), help-box use none, last semester's marks a prior only that fades fast.
  • Forgetting: uncertainty grows with time, which a 14-week semester needs.
  • Bloom levels are not assumed to be a strict ladder. Which levels depend on which is tested.
Feeds

C3 reads a Bloom-aware target per step. C4 uses the per-level record in its progression policy, which today keeps its own bloom block that C2 does not provide.

Measure

Prediction and calibration with per-level mastery against concept-level mastery, using C1's real graph instead of a placeholder.

COMPONENT 3 / CHAMUDITHA H V C

Adaptive, behaviour-aware, negotiable path planner

Uniqueness: a learning path that stays verified while it changes in real time. It reacts to the learner's behaviour, fits their deadline and lets them skip what they know, and every change passes the symbolic critic first.

GPT-4o alone: 21/36 faulty With critic and repair: 0/36 Repair rounds: 0.6 average Graph: 14 concepts
Extra detail in this section

This component has a full build plan below: trigger rules, new critic rules, a code layout, data contracts, a week-by-week schedule to PP2 and a demo script.

Where it stands

  • GPT-4o drafts 3 paths; the critic checks 5 rules and returns typed violations such as MissingPrerequisite(Heap, needs=Tree).
  • Only the broken step is repaired (up to 3 rounds), with a topological sort fallback.
  • Offline RL (IQL) is planned to rerank verified paths only.

What the panel will see as thin

  • A topological sort is also 0% faulty, so the value of the LLM is not shown yet. This is the first question they will ask.
  • The path is computed once and never changes, even if the student struggles or gets bored.
  • No deadline, no time budget, no forgetting, and no way for the learner to say "I already know this".
  • Offline IQL on MOOCCubeX is heavy and may not finish in time.

Fix first

  • Move to the real C1 graph (84 concepts) and real C2 mastery and uncertainty values.
  • Repeat every experiment at least 3 times (LLM output varies) and report mean and spread.
  • Add a stronger baseline, "smart topo": a topological sort that skips concepts the learner has already mastered. If C3 only beats the plain topological sort, the panel will not accept it.
  • Try a second, cheaper proposer (an open model through Ollama) to show the critic works with any LLM.

What to build

ADD-ON 3.1

Event-driven runtime replanning

MustResearch

The path becomes live. C3 listens to learner state updates from C2 and the behaviour layer. When a trigger fires, it re-plans only the remaining part of the path, the critic checks it, and a change log records why. C4 can then tell the learner "your path changed because...".

TriggerCondition (starting values, tune later)Action on the remaining path
STRUGGLE2 or more wrong answers on the current concept, and confusion for 3+ windows or response time above the 80th percentileInsert a review of the weakest prerequisite, or switch to another resource for the same concept
FAST_MASTERYMastery above 0.85 with a narrow interval after a probeRemove later steps that re-teach what is now known
DISENGAGEDBored or away for 4+ windows, or 3+ tab switches in a stepChange modality (video to interactive exercise or visual trace); keep the order
FRUSTRATEDFrustration high for 3+ windowsNext step must not be harder (new rule R8); offer an easier worked example
REVIEW_DUEPredicted recall of a needed concept falls below 0.6 (Add-on 3.2)Insert a short review before the dependent concept
  1. Re-plan only the suffix: keep completed steps, send the remaining target and new learner state to the proposer, then run the critic and typed repair as today.
  2. Debounce: re-plan only at step boundaries and at most once per step. This avoids a path that changes every minute. Track a stability metric (changes per session).
  3. Write every change to a change log: {time, trigger, before, after, rule_ids}. The UI and C4 read it.
ADD-ON 3.2

Deadline-aware schedule with spaced review

MustResearch

Real students plan around exams. The learner gives a target, a deadline and minutes per day. C3 estimates time per concept, splits the path into sessions, and inserts short reviews before forgetting sets in. If the plan does not fit, the LLM explains the trade-off and offers options.

  1. Time model: base minutes from C1 cognitive load, scaled by the learner's own pace from C2 response times.
  2. Forgetting model: half-life regression (Settles and Meeder, 2016) per concept, which predicts recall from time since last practice and practice history.
  3. Mark which concepts are mandatory (prerequisites of the target) and which are optional. If time is short, drop optional ones first, then offer "extend the deadline" or "reduce the target".
  4. Add three new critic rules, so the new behaviour is verified like the old one:
RuleCheckTyped violation
R6Total estimated time fits before the deadlineOverBudget(minutes_over)
R7Any due review comes before the concept that depends on itReviewMissing(concept, before)
R8No difficulty increase right after a frustration signalPacingAfterFrustration(step)
ADD-ON 3.3

Verified skip and an explainable roadmap

MustUXResearch

The learner sees the path as a visual roadmap with today's session highlighted. They can tap "I already know this" on any step. Before the step is removed, C3 asks C4 for a 2 to 3 question probe at that concept's Bloom level. Pass: the step is skipped and the critic re-checks the path. Fail: the step stays, and the learner sees what they missed. "Why this step?" shows the rule behind it, for example "Heap needs Tree first". The probe questions can reuse C4's teach-back test items, which are tagged by concept and Bloom level and have answers taken from the verified graph.

Research angle

How often are learners' "I know this" claims wrong? How much time does verified skip save compared with a forced full path, without lowering post-test scores?

Why it matters

It answers the classic objection to rule-based systems (rigid, no learner control) while keeping correctness.

ADD-ON 3.4

Contextual bandit selector over verified options

ShouldResearch

Replace full offline IQL for PP2 with a contextual bandit. It is easier to train, easier to explain and fits the "choose among verified options" design. IQL can stay as a post-PP2 comparison or future work.

  • Choices: the verified candidate paths, and for each step the resource type (C1 video segment, C4 text explanation, C4 visual trace, coding exercise).
  • Context: mastery and uncertainty summary, current affect, time left before the deadline, which resource types worked for this learner before.
  • Reward: mastery gain per minute, minus a penalty for disengaged windows.
  • Method: LinUCB or Thompson sampling (a small NumPy implementation is enough), trained in the learner simulator.
  • Safety: the bandit can only pick options that passed the critic. The invariant from PP1 stays exactly the same.
ADD-ON 3.5

Learner simulator (shared with C4)

MustInfrastructure

Every C3 result needs learners to test on, and C4 already uses a ZPD-based simulator. Build one shared simulator and own it with C4.

  • Knowledge state per concept. Learning gain depends on prerequisite mastery (knowledge space theory, ZPD).
  • Forgetting with exponential decay between sessions.
  • Simple affect dynamics: frustration rises with repeated failure, boredom with items that are too easy.
  • Resource preference per simulated learner, so the bandit has something to learn.
  • Several learner profiles (fast, slow, overconfident, easily bored) to show where C3 helps and where it does not.
ADD-ON 3.6

Block plan with a mastery floor

ShouldResearchSuggested by C4

Extend the deadline-aware schedule (3.2) from one path to one target into a plan for a whole 7-week block, so the goal is "nobody left under the floor", not "one valid path".

  • Goal: every student reaches a minimum mastery floor on every concept in the block, at the Bloom level the course sets, before the exam. This is mastery learning and does not promise equal outcomes.
  • Allocation: gap = target minus current mastery. Spend practice in proportion to the gap, weighted by how many later concepts depend on the concept, in prerequisite order.
  • Projection: estimate each student's learning rate and project to the exam date. If the projection ends under the floor, escalate (more practice, a nudge, a lecturer alert). Re-plan at checkpoints in weeks 3 and 10.
  • Fairness: strong students get stretch tasks at higher Bloom levels, not less work. The student sees why they got their plan. Nobody gets less than the baseline.
Measure

Share of simulated students under the floor and the spread of exam scores, against a uniform plan and a performance-tiered plan.

ADD-ON 3.7

Cohort simulation and audited-edge rules

ShouldResearchSuggested by C4

Make the comparison with the topological sort meaningful, and use what the graph audit finds.

  • Cohort simulation: C4's simulator already creates simulated learners. A simulated class of 300 with a floor makes the equalisation claim testable before any real student. Report time to reach the floor, practice spent on real gaps and the share of students under the floor, not only violations.
  • Audited edge confidence: rule R1 on an edge the auditor calls Unsupported may force unnecessary work, and a Missing edge may leave a gap. Compare path validity before and after the audit.
  • Bloom-aware steps: each step carries a target Bloom level from C4's progression policy.
  • The rule that learned selection chooses only among verified options stays unchanged.

Questions the panel will likely ask

A topological sort is also 0% faulty. Why do you need an LLM?

Validity is the floor, not the goal. C3 is compared with smart topo on time-to-mastery, redundant steps, retention under a deadline and learner preference. Smart topo cannot probe uncertainty, fix misconceptions first, react to behaviour or fit a deadline.

If the path keeps changing, won't students get confused?

Replanning happens only at step boundaries, is debounced, and every change is explained. Stability (changes per session) is measured and reported.

Can the bandit break correctness?

No. It only chooses among options that passed the critic, the same invariant as the planned RL layer.

ADD-ON 4.1

Teach-back exam with a knowledge-restricted AI novice

MustResearch

In a supervised exam, the student explains a lecture's concepts in writing ("Explain X in your own words, and include Y and Z"). A novice AI that may answer only from the student's text then takes a fixed hidden test, tagged by concept and Bloom level, with answers taken from the verified graph. The novice's score, broken down by concept and level, is evidence of what the student understands. Any explanation the student gives is also checked by C4's existing claim verifier.

  1. Coverage: check that the required graph concepts appear in the explanation.
  2. Claim check: run the existing C4 verifier on the student's claims. Contradictions of known-false statements are flagged.
  3. Novice test: the novice sees only the student's text, supplied as retrieved context, with an "I don't know" option. Test items are multiple choice or short answers matched against graph facts, so scoring has no LLM judge and no scoring variance. Only the novice's own answers vary, and those are measured with repeated runs.
  4. Evidence: a score per (concept, Bloom level) with an uncertainty, sent to C2.
  5. Depth check: trace each correct novice answer to a sentence in the student's text and discount answers the novice reasoned out on its own, so a short keyword answer cannot score well.

Worked example (heaps). Prompt: "Explain what a heap is in your own words. Your answer must include 'complete binary tree' and 'stored in an array'." The student writes 4 to 8 sentences. Coverage and the claim check run first ("a heap is always fully sorted" matches a known-false statement and is flagged). The novice then takes the hidden heap test and returns, for example, Remember 3 of 3, Apply 1 of 2, Analyze 0 of 1. A lab exam of 6 lectures at about 10 minutes each fits one hour. A second mode, where the student answers the novice's questions, comes later because it is richer but noisier.

Student taskNovice test itemLevel evidenced
Explain XDefine or recognise XRemember, Understand
Include an exampleApply X to a new caseApply
Compare X and YChoose and justifyAnalyze
Answer the novice's "why?" (later mode)Judge a flawed designEvaluate

This task-to-level mapping is a hypothesis that RQ4i tests, not an assumption.

  • Validity tests (first gate): leakage (an empty explanation must score near chance), discrimination (complete, missing a step, shuffled, subtly wrong and empty explanations must rank in that order), reliability (repeated runs give nearly the same score). If the novice cannot pass these, stop and report the negative result.
  • Fairness: test whether weaker English writers score lower at the same level of understanding. Compare prose with a structured option (concept list or labelled diagram).
  • Gaming: pasted AI-written answers measure the AI. Use a supervised lab setting, unseen prompts, similarity checks and a short oral follow-up on a sample.
  • Test difficulty: pilot the hidden items and keep only those that spread students out, because an easy quiz gives a ceiling effect.
  • Stakes: formative first. Count towards a grade only after validity and fairness are shown.

ADD-ON 4.2

Graph Auditor

MustResearch

The graph is treated as ground truth by C4, but nobody checks it against what students do. The auditor reads the graph (C1) and student evidence (C2) and gives the lecturer a report. It proposes; a lecturer decides, and nothing changes automatically.

  1. Edge audit. For each "A is a prerequisite of B": an implication test (mastering B without A should be rare after allowing for guess and slip), an order test and a lift test. Each edge gets a status with an interval: Supported, Contested, Reversed, Unsupported or Missing (candidate).
  2. Bloom audit. Items labelled higher should be empirically harder, and success at higher levels should depend on success at lower ones. Disagreements are reported as findings about the label, not corrected. Bloom labels are tags on items and on a student's level within a concept, not prerequisite edges.
  3. Misconception audit (only if the data records which wrong option was chosen).
  4. Loop back into C4. A claim that relies on a contested prerequisite becomes INCONCLUSIVE instead of a hard violation, and an unsupported edge no longer sends a student to "review X first". The report gains an edge_confidence block.
Edge type (from C1)What the audit tests
prerequisite-ofThe edge audit above
bloom-levelItems labelled higher should be harder, and success at higher levels should depend on lower ones. A disagreement is reported as a finding about the label, because Bloom is not a strict ladder.
cognitive-loadDoes the computed load (from prerequisite depth) predict how hard students find the concept?
common-misconception-ofIf the data records which wrong option was chosen, is the misconception really common? Skipped otherwise.
 
Audit proposal  (C4 to C1, for the curation console)
{"edge": ["binary_tree", "heap"], "status": "Contested",
 "evidence": "lift 1.1 (0.8 to 1.6), n=120",
 "proposal": "keep, lower confidence", "needs_lecturer": true}
Measure

Plant known errors (delete, reverse, add a fraction of edges) and report precision, recall and F1 across data sizes. Then run on ASSISTments against co-occurrence and ordering baselines. Finally, count wrong "review first" instructions and missed prerequisites with and without audited edges.

Link to C1

C1 Add-on 1.2 tests edges against learner data and C1 owns the curation console. C4 supplies the audit method, the Bloom audit and the loop back into verification, and C1 applies the changes a lecturer approves.

Limits

Students meet prerequisites first because the course runs in that order, so the order and implication tests can look like dependencies when they are only the timetable. Mitigations: compare lecturers or offerings that teach in a different order, control for prior mastery, and rely on the planted-error test. ASSISTments is not Data Structures, so auditing the DSA graph needs DSA performance data. Small classes give wide intervals, so many edges will honestly be Contested. Statuses are evidence, not proof.

ADD-ON 4.4

Execution-grounded visual explanations

ShouldResearch

For a small set of operations, run real reference code, record the state after every step and turn it into a step-through picture. The LLM writes narration as claims tied to step numbers, and each claim is checked against the recorded state. "5 swaps with its parent 9" is either true in the trace or it is rejected and repaired.

  1. Instrumented reference implementations for 4 to 5 operations first (heap insert, BST insert, BFS, binary search, stack), growing to 10 to 12 if time allows. Each records a JSON snapshot after every step.
  2. Ask the LLM for narration as [{step: 3, claim: "5 swaps with parent 9"}, ...]. Verify each claim against the trace and the graph. Type the errors (WrongState, WrongOrder, UnsupportedFact) and repair only the broken sentence.
  3. Render the trace as SVG frames the learner can step through, and let the learner enter their own values.
Feeds

C3 can choose "visual trace" as a resource type. The same trace checker can check a student's claims in the teach-back exam when they describe a step-by-step process.

Claim-level error rate before and after verification; share of explanations with zero unsupported claims.

ADD-ON 4.7

Semester plan and help box (demo)

ShouldUX

Shown as a simulation and a small demo, not a built LMS.

  • Goal: for each 7-week half, every student reaches a minimum mastery floor on every concept before the exam, and the spread between students shrinks. This is mastery learning; it does not promise equal outcomes. Measured by the share of students under the floor and the spread of exam scores.
  • Allocation: gap = target minus current mastery at the target Bloom level. Practice is spent in proportion to the gap, weighted by how many later concepts depend on the concept, in prerequisite order. Last semester's marks are only a fast-fading prior.
  • Projection: estimate each student's learning rate and project mastery to the exam date. If it ends under the floor, escalate (more practice, a nudge, a lecturer alert). Re-plan at checkpoints in weeks 3 and 10.
  • Fairness: strong students get stretch tasks, not less work. The student sees why they got their plan and can ask for more. Nobody gets less than the baseline.
  • "Need help with a concept?" box: graph facts and lecture chunks, an LLM draft, then the existing C4 verification and repair. The student attempts first, then gets tiered hints, then the explanation. Help requests give the lecturer a confusion map per concept. Asking for help is never mastery evidence.
  • Fit with C3: this uses C2 mastery and should call C3's planner where possible instead of duplicating it. A simulated class of 300 learners (the existing simulator) makes the floor-and-spread claim testable before any real student.
ADD-ON 4.8

Layered, versioned graph (demo)

CouldUX

"Dynamic" means layers, versions and proposals, not a graph that rewrites itself.

  • Layers: a base graph at department level that changes rarely; a lecturer overlay per lecturer and offering (reorder, add local concepts, mark "not covered", change emphasis, add terms); audited edge confidence per offering from the Graph Auditor.
  • Governance: changes come from weekly re-reading of lecture transcripts, audit results and lecturer edits. Every change is a proposal that a lecturer approves, with a version and a changelog. The graph is frozen for each 7-week block so students are not tested against a moving target.
  • Mastery under change: a split gives the children the parent's mastery with added uncertainty; a merge takes the lower mastery and combined uncertainty; a new edge triggers a re-check, not a demotion.
  • Needs C1's agreement, so it is shown as a small demo only.

Questions the panel will likely ask

Isn't this just an LLM grading an essay?

No. The student is not graded by an LLM's opinion. A restricted novice takes a fixed test whose answers come from the verified graph, so the scoring step has no LLM judge. Whether that score is valid, reliable and fair is the research question, and a negative result is a valid finding.

Doesn't the LLM already know the answers?

That is the leakage test. With an empty explanation the novice must score near chance on the restricted concepts. Prompting alone is known to leave real knowledge intact, so retrieval-only context comes first and unlearning is the fallback.

Isn't this idea already done?

LLM teachable agents exist, and a Waterloo project plans an exam on what an LLM learned. We found no published result for using the novice's score as a validated, per-level assessment tied to a verified graph. We state the contribution as a validation protocol and the graph integration.

Isn't the graph audit C1's job?

C1 builds the graph and the curation console. C4 checks the graph against student data and feeds the result back into verification. The split is agreed with C1 and written down.

What exactly do you claim?

We evaluate whether the novice's score is a valid, reliable and fair indicator of a student's understanding, and we give a protocol for checking it. We do not call it validated before the data exist. We do not claim equal outcomes for every student, that Bloom levels form a strict ladder, or that the layered graph is a research result.

Your learning gains are simulated. Will you test with students?

Yes, after ethics approval: novice score versus conventional exam, a human grading sample, a fairness comparison, and lecturer agreement on audited edges.
